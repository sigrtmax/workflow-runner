# Workflow Runner

NestJS-сервис исполняет заранее описанные процессы: нормализует заявку, отправляет
её в CRM, проверяет HTTP-результат и передаёт данные в ERP. Определение — конечный
ациклический граф с четырьмя типами шагов: HTTP, условие, задержка, преобразование.

PostgreSQL хранит версии, входы, результаты, попытки, сроки ожидания и журнал.
BullMQ передаёт уведомления о готовых шагах. Планировщик восстанавливает их из БД,
поэтому перезапуск worker и потеря очереди не требуют повторного запуска процесса.

API и worker запускаются отдельно из одного приложения. Захват шага защищён
транзакцией, lease и token; общий лимит действует на все worker-процессы одной БД.
HTTP выполняется вне транзакции. Результат, журнал и открытие зависимых узлов
фиксируются атомарно.

## Запуск

Нужны Node.js 22.17+ в ветке 22.x, npm, Docker с Compose. Команды выполняются
из корня репозитория. API слушает `127.0.0.1`; публичный доступ и авторизация
не входят в эту поставку.

```sh
npm ci
# Выбранные в примере порты 54329 и 63799 должны быть свободны.
docker compose --env-file .env.example -p workflow-runner-local up -d --wait
set -a
. ./.env.example
set +a
npm run migrate
npm run build
npm start
```

Во втором терминале загрузите те же переменные и запустите `npm run worker`.
Приложение само не читает `.env`: параметры приходят из окружения процесса.
`INTEGRATIONS_JSON` задаёт разрешённые адреса CRM/ERP. При изменении портов
согласуйте URL и `WORKFLOW_POSTGRES_PORT` / `WORKFLOW_REDIS_PORT`.

Опубликовать [пример процесса](examples/lead-to-erp.json) и запустить его:

```sh
curl -i http://127.0.0.1:3000/workflows/leads/versions \
  -H 'Content-Type: application/json' --data-binary @examples/lead-to-erp.json
curl -i http://127.0.0.1:3000/executions \
  -H 'Content-Type: application/json' -H 'Idempotency-Key: synthetic-lead-001' \
  -d '{"workflowName":"leads","version":1,"input":{"email":" SAMPLE@EXAMPLE.TEST ","amount":"1250"}}'
```

CRM `/leads` и ERP `/orders` должны возвращать `201` и поддерживать стабильный
`Idempotency-Key`. Адреса в `.env.example` — места для локальных интеграций;
сам Compose поднимает только PostgreSQL и Redis. Полный сценарий с HTTP-стендом,
включая аварийный restart, воспроизводится тестами ниже.

Ответ запуска содержит `id`. Состояние: `GET /executions/:id`, журнал:
`GET /executions/:id/events`. Остальные запросы — в
[examples/requests.http](examples/requests.http), контракт — в [docs/api.md](docs/api.md).

Остановка инфраструктуры сохраняет данные:

```sh
docker compose --env-file .env.example -p workflow-runner-local down
```

## Поведение при сбоях

- Повтор запуска с тем же ключом и содержимым возвращает существующий execution.
  Другой вход или версия с тем же ключом дают `409`.
- Retry ограничен бюджетом и backoff. Обычные `4xx`, ошибки данных и дефекты
  приложения требуют ручного решения. `408`, `429`, `5xx`, timeout и транспортные
  ошибки повторяются только при безопасной операции.
- `pause` прекращает новые захваты; уже отправленный HTTP-запрос может завершиться.
  `resume` сохраняет результаты и сроки. `retry` повторяет только упавшие узлы.
- После неопределённого результата небезопасного запроса автоматического повтора
  нет. Ручной retry требует `confirmUnknownOutcome: true`.
- Параллельные ветки не меняют общий объект данных. Слияние ждёт все активные входы;
  невыбранные ветки пропускаются. Задержка хранится в БД и не занимает слот worker.

Гарантия однократного внешнего эффекта зависит от получателя. Одного заголовка
недостаточно: CRM/ERP должны действительно сохранять и проверять ключ.
Лимит конкурентности ограничивает действующие leases; сервер интеграции может
продолжить обработку после локального timeout.

## Наблюдаемость

Контекст корневого span принятия запуска сохраняется в PostgreSQL. Попытки шагов
после restart используют тот же trace ID и передают `traceparent` в интеграции.
Корневой span завершается после принятия запуска; полная длительность процесса
вычисляется по `createdAt` и `finishedAt`.

Опциональный `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318` включает OTLP HTTP
экспорт на `/v1/traces` и `/v1/metrics`. Без него внешний collector не нужен.
Метрики: `workflow.step.duration` в секундах и `workflow.step.errors`, с метками
имени процесса, версии, узла, типа шага и результата. Идентификаторы запусков
и содержимое запросов не попадают в метки. Логи содержат только разрешённые
поля корреляции; подробная история переходов хранится в журнале БД.

Аварийно оборванный span может не экспортироваться. Телеметрия не заменяет
транзакционный журнал и не обещает точного учёта событий при падении процесса.

## Проверки

Тестовый Compose использует отдельные volumes, сеть и случайные loopback-порты.
Каждый интеграционный набор создаёт отдельную БД и собственный префикс очереди.
Тесты удаляют только свои базы и задания.

```sh
docker compose --env-file /dev/null -p workflow-runner-test up -d --wait
npm test -- --runInBand
npm run typecheck
npm run build
npm run lint
npm run format:check
docker compose --env-file /dev/null -p workflow-runner-test down
```

В сквозных тестах настоящие PostgreSQL, Redis, HTTP-сервер и отдельные worker-процессы.
Проверяются `SIGKILL` после принятия CRM-запроса, стабильные ключ и trace, восстановление
задержки, конкуренция двух worker, pause/resume и ручной retry. Чистые тесты отдельно
проверяют граф, преобразования, классификацию HTTP-ошибок и backoff.

[Проектные решения и инварианты](docs/design.md), [статус проверок](docs/STATUS.md).
Визуального конструктора, произвольного JavaScript, циклов, компенсаций и
универсального механизма расширений здесь нет.
