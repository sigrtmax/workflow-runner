# Workflow Runner

Контракт исполнения. Проверенные сценарии описаны в [STATUS.md](STATUS.md).

## Назначение и границы

Сервис выполняет версионируемые процессы: получает данные заявки, преобразует их,
отправляет в CRM, проверяет HTTP-результат и при успехе передаёт данные в ERP.
CRM в демонстрационном сценарии возвращает `201 Created`; ошибки выражаются через
HTTP-статусы. Входящие callback и ожидание внешних событий не нужны.

В ядре ровно четыре типа шагов: HTTP-запрос, условие, задержка и преобразование
данных. Параллельность задаётся рёбрами графа, а не дополнительным типом шага.
Ручная обработка — сохранённое проблемное выполнение, доступное через API и журнал;
отдельный интерфейс оператора не входит в проект.

Не входят: визуальный редактор, произвольный JavaScript или вычисляемые выражения,
циклы, вложенные процессы, компенсации, динамическое создание графа, callback,
мультитенантность, RBAC, публичное размещение и универсальная платформа интеграций.
Первый вариант рассчитан на локальный запуск доверенным оператором.

## Архитектурный выбор

Используется одно модульное NestJS-приложение с двумя точками запуска: HTTP API
и worker. Один репозиторий, одна модель данных, один набор миграций. Отдельный
процесс worker нужен для проверки восстановления без остановки API.

Альтернатива — собрать граф целиком в BullMQ Flow. Это уменьшит собственную
координацию, но перенесёт важную часть состояния графа в Redis и усложнит
восстановление из PostgreSQL. Не выбирается из-за требования к источнику истины.

Другая альтернатива — универсальный оркестратор с плагинами, событиями и отдельными
сервисами. Для четырёх фиксированных шагов она добавляет границы без потребителей.

Стек: NestJS, TypeScript со strict-проверками, PostgreSQL через `pg`,
BullMQ, Redis, OpenTelemetry, Jest и Supertest. SQL нужен для явных транзакций,
блокировок и конкурентного захвата задач; ORM пока не даёт необходимого преимущества.
Версии зафиксированы в lockfile.

Модули выделяются по назначению: определения процессов, исполнения, worker.
Контроллеры проверяют HTTP-контракт. Предметные переходы находятся в сервисах;
SQL-операции атомарного запуска, захвата и завершения — в соответствующем repository.
Чистые функции проверяют граф и исполняют условие/преобразование. Общего BaseService,
интерфейса для каждого класса и собственного реестра плагинов не будет.

## Определение процесса

JSON содержит имя, версию, узлы, зависимости и настройки конкретных шагов.
Опубликованная версия неизменяема; новое содержание создаёт новую версию.
Запуск закрепляется за конкретной версией. Обновление определения не влияет на
уже созданные исполнения.

Граф конечный и ациклический. Проверяются уникальность идентификаторов, существование
ссылок, отсутствие циклов, достижимость узлов и корректность зависимостей данных.
Ссылка на результат допустима только для предшествующего узла; отсутствующий
результат не превращается молча в `null`.

HTTP-шаг задаёт именованную интеграцию, относительный путь, метод, входные данные,
ожидаемые статусы, timeout и политику повторов. Для CRM ожидается `201`.
Произвольные адреса в определениях запрещены: адреса интеграций берутся из
разрешённой локальной конфигурации. Redirect отключён; время и размер ответа ограничены.
Это защищает доступ к внутренним адресам через пользовательское определение.

Условие поддерживает фиксированные проверки `eq`, `ne`, `gt`, `gte`, `lt`, `lte`
и `exists`, с явными выходами `true` и `false`. Преобразование — отображение полей
из входа и результатов предков, литералы и фиксированные операции `trim`,
`lowercase`, `toNumber`. Некорректный тип или число — явная ошибка данных.
Записи по опасным ключам прототипа отклоняются.

Задержка сохраняет срок в PostgreSQL и освобождает worker. Перезапуск не начинает
ожидание заново. Задержка не занимает слот активного исполнения шага.

Узлы независимых веток выполняются параллельно. При слиянии должны завершиться
все активированные входящие зависимости. Решения по невыбранным рёбрам сохраняются;
узел без активных входов пропускается. Пока выбор любой входящей ветки неизвестен,
узел слияния не запускается. Неявной общей изменяемой переменной между ветками нет.

## Состояние и инварианты

Минимальные таблицы: `workflow_definitions`, `workflow_executions`,
`step_executions`, `step_attempts`, `execution_events`.
Определение хранит граф, execution — вход и закреплённую версию, step — результат,
состояние, срок готовности и lease, attempt — историю попыток, event — журнал
значимых переходов. Выбор рёбер условия сохраняется вместе с результатом узла.

1. `UNIQUE(name, version)` защищает версии, опубликованное содержание не обновляется.
2. `UNIQUE(idempotency_key)` защищает создание запуска даже при конкурентных запросах.
   Канонический fingerprint включает имя, версию и вход. Повтор с тем же содержимым
   возвращает тот же execution; тот же ключ с другим содержимым даёт `409`.
3. Для пары execution/узел существует одна запись шага. Повторы добавляют attempts,
   не дублируют сам узел и не перезаписывают историю.
4. Захват шага атомарно проверяет состояние исполнения, готовность, lease и лимит
   конкурентности. Каждая попытка получает token; устаревший worker не может
   завершить шаг или открыть его потомков.
5. Результат шага, завершение attempt, журнал и открытие зависимых узлов записываются
   одной транзакцией. HTTP-вызов выполняется вне транзакции.
6. Успешные узлы неизменяемы. Retry не повторяет успешных соседей или предков.
7. BullMQ содержит уведомления о готовой работе. Истиной остаются записи PostgreSQL.

Состояния исполнения: `running`, `paused`, `failed`, `succeeded`.
Состояния шага: `pending`, `ready`, `running`, `waiting`, `succeeded`, `failed`,
`skipped`. Временная ошибка переводит шаг в `waiting` до следующей попытки;
окончательная ошибка сохраняет причину и требует ручного решения.

## Очередь, восстановление и конкурентность

Планировщик периодически выбирает готовые и просроченные записи из PostgreSQL
и отправляет идентификаторы в BullMQ. Для исходной небольшой нагрузки это проще
отдельной outbox-таблицы: готовый шаг уже является сохранённым намерением выполнить
работу. Сбой между commit и enqueue закрывается следующим проходом планировщика.

ID уведомления включает счётчик попыток шага: старое активное задание BullMQ
не задерживает новую попытку после восстановления lease.
Повторная доставка задания безопасна на уровне состояния: worker сначала захватывает
шаг в БД. Потеря Redis восстанавливает уведомления из сохранённых сроков и состояний.
Зависшие попытки обнаруживаются по истечению lease. Для чистых шагов восстановление
после потери lease ограничено тремя попытками; обычный дефект приложения не повторяется. Heartbeat продлевает только
текущий lease; после потери владения worker не фиксирует результат.

Один настраиваемый общий лимит ограничивает количество одновременно захваченных
шагов во всех worker-процессах. Проверка числа действующих leases и захват защищены
общей транзакционной блокировкой PostgreSQL. Локальная concurrency BullMQ ограничивает
число обработчиков процесса. Настроек лимитов по клиентам и интеграциям не будет.
Лимит относится к действующим попыткам ядра: уже отправленный запрос во внешней
системе невозможно гарантированно остановить локальным timeout.

## Ошибки и повторные попытки

Ошибка входа отвергается до сохранения запуска. Ошибка преобразования или обычный
`4xx` окончательны. `408`, `429`, `5xx` и транспортные ошибки могут быть временными,
но повтор разрешён только при доказанно безопасной операции. Неожиданный успешный
статус также является нарушением контракта, а не автоматическим успехом.

Для HTTP заранее задаётся одна из политик: безопасная операция без побочного эффекта,
поддерживаемый получателем idempotency key или запрет автоматического повтора.
Сохранённый результат ограничен 1 MiB и вложенностью JSON до 32. Строки и ключи
с NUL или непарными суррогатами Unicode отклоняются до записи в JSONB.
Сам заголовок не гарантирует идемпотентность — интеграция должна его обрабатывать.
При поддержке ключа все попытки одного execution/узла отправляют один ключ и один payload.

Retry ограничен числом попыток; экспоненциальный backoff имеет верхнюю границу.
Решение о повторе, счётчик и `next_attempt_at` находятся в PostgreSQL. BullMQ
не ведёт независимый бюджет повторов бизнес-операции. Для `429` учитывается валидный
`Retry-After`; если ожидание выходит за предусмотренные ограничения, нужен оператор.

Timeout прерывает локальный HTTP-запрос через AbortController. Если результат
запроса с побочным эффектом неизвестен и получатель не поддерживает идемпотентность,
автоматического повтора нет. Это относится и к восстановлению просроченного lease.
Состояние и журнал явно указывают неопределённый результат.

В демонстрационной CRM и ERP реализуется приём стабильного idempotency key.
Тест воспроизводит сбой после принятия запроса и до сохранения локального результата.
Утверждения об exactly-once для произвольного внешнего HTTP API не будет.

## Управление и HTTP-контракт

- `POST /workflows/:name/versions` — опубликовать проверенное определение.
- `GET /workflows/:name/versions/:version` — прочитать конкретную версию.
- `POST /executions` с `Idempotency-Key` — запустить конкретную версию.
- `GET /executions/:id` — состояние и результаты узлов.
- `GET /executions/:id/events` — журнал с курсорной пагинацией.
- `POST /executions/:id/pause` — остановить выдачу новых шагов.
- `POST /executions/:id/resume` — продолжить приостановленное исполнение.
- `POST /executions/:id/retry` — возобновить с окончательно упавших шагов.

Pause фиксируется в БД и сериализуется с захватом шага. Уже захваченные запросы
могут завершиться; новых после фиксации pause не будет. Их результаты сохраняются.
Resume сохраняет результаты и сроки ожидания; истёкшая задержка готова сразу.
Терминальные исполнения pause/resume не оживляют. Повтор pause или resume безопасен.

После окончательной ошибки новые шаги не захватываются, уже запущенные завершаются.
Ручной retry допускается после их завершения/восстановления: сбрасывает только
упавшие шаги, сохраняет успешные и продолжает граф. При нескольких ошибках в
параллельных ветках повторяются все упавшие узлы этого исполнения. Новые attempts
сохраняют предыдущую историю; ручной retry получает новый ограниченный бюджет.
Для неопределённого результата небезопасного HTTP-запроса API требует отдельного
явного подтверждения риска дублирования. Изменять вход или версию при retry нельзя.

API доступен только локально. В этой поставке нет логина, refresh, ролей и
пользовательских сессий. Доступ из публичной сети требует отдельного решения об auth.

## Наблюдаемость

У исполнения один trace ID: корневой span принятия запуска создаётся один раз,
его контекст сохраняется в БД. Попытки шагов и продолжения после restart извлекают
этот контекст. Корневой span не удерживается в памяти всё время ожидания; длительность
workflow вычисляется из сохранённых времён. В HTTP интеграции передаётся trace context.

OpenTelemetry экспортирует длительность попыток и счётчик ошибок по имени процесса,
версии, узлу, типу шага и ограниченному классу результата. execution ID, payload,
URL и текст исключения не используются как метки метрик. Контекст workflow не
подмешивается произвольно к другому входящему запросу API.

Журнал сохраняется транзакционно с переходами. Структурированные логи содержат
request ID, execution ID, step ID, attempt и trace ID. Payload, заголовки авторизации
и тела ошибок внешних сервисов не логируются. Сохранённые входы/выходы нужны движку,
поэтому они ограничены по размеру и доступны через локальный API; пример использует
синтетические данные. Секреты не хранятся в определениях и результатах.

Телеметрия диагностическая: аварийно оборванный span может не экспортироваться,
а метрики не заменяют журнал в БД. Тест проверяет общий trace ID до и после restart.
Grafana, Prometheus и отдельный кластер мониторинга в поставку не добавляются.
